# 版本复现与并发语义

## 1. 为什么结论可复现

每次准入判定都生成一条**不可变记录**，包含：

- 资源清单的深拷贝快照与资源指纹（sha256，规范化 JSON）；
- 引用的策略名、策略版本号、策略内容指纹（64 位 sha256）；
- 每条规则的命中依据（规则 id、实际值/期望值、严重级别、豁免 id、理由）；
- 最终处置 `action`、汇总理由 `rationale` 与判定时刻。

判定完成后记录不再被修改。随后发布新策略版本、撤销豁免、重放判定，
都不会覆盖历史记录。

策略指纹 = `sha256(canonical_json({raw_document, rules}))`，
加载策略时从磁盘内容**当场重算**，因此即使有人手工篡改策略文件
并连 `fingerprint` 字段一起伪造，也无法与判定记录里固化的指纹对齐。

## 2. 复现流程

```
POST /api/decisions/{decision_id}/replay
```

或服务层 `Evaluator.replay(decision_id)`：

1. 读取不可变判定记录（含资源快照、策略版本、策略指纹）；
2. 按 `name + version` 取策略，重算磁盘内容指纹并与记录中的指纹比对，
   不一致则以 `policy_version_conflict` 拒绝复现；
3. 在**历史判定时刻**冻结时钟，按记录中固化的“规则 → 豁免 id”采纳关系
   重算（豁免事后被撤销/过期不影响历史结论）；
4. 逐字段比对 action、rationale、全部命中依据；
5. 完全一致返回 `consistent: true` 以及 stored/recomputed 两份明细；
   任何不一致都以错误拒绝，而不是静默返回“看起来成功”。

因此：同一资源 + 同一策略版本 + 同一策略指纹 ⇒ 唯一确定的结论。

## 3. 并发与幂等

### 幂等键

- 准入：`POST /api/admit` 可带 `idempotency_key`；
- 豁免申请同理。

同一幂等键的重复/并发提交：

- 返回首次产生的记录（响应中 `idempotent_hit: true`）；
- 不新增判定/豁免记录，不产生重复副作用；
- 即使两次提交的负载不同，也以**首次提交**为准（首决确定性）。

不带幂等键的每次提交都是独立判定，生成不同记录。

### 并发控制

- 每个聚合一个 JSON 文件（`policies.json` / `decisions.json` /
  `exemptions.json`）；
- 进程内：`threading.RLock` 串行化临界区；
- 跨进程：`fcntl.flock` 对旁路锁文件加排他锁；
- 写入：临时文件 + `fsync` + `os.replace` 原子替换，读者只会看到完整文件；
- “先查幂等键 → 评估 → 锁内最终裁决落盘”，因此多线程/多进程并发提交
  同一幂等键时，最终恰好有一条记录且所有调用方看到同一结论。

非法状态流转（豁免状态机）在锁内再次校验，保证并发
approve/reject 只有一个方向成功。

## 4. 数据文件

默认位于 `./data`（可通过容器构造参数替换为任意目录，测试使用临时目录）：

```
data/
├── policies.json     # 全部策略的全部不可变版本
├── decisions.json    # 全部判定记录（含资源快照）+ 幂等键索引
├── exemptions.json   # 豁免记录 + 幂等键索引
└── *.json.lock       # fcntl 跨进程锁文件（自动创建）
```

全部为本地 JSON，无外部数据库、无网络依赖。
